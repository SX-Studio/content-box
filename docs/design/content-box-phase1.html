01

Scope & non-goals

Fase 1 levert het fundament waar al het andere op rust: een geverifieerde identiteit, een box, en een veilige manier om mensen erin uit te nodigen. Alles wat content, geld of moderatie raakt is bewust uitgesteld.

In scope

Wat Fase 1 bouwt

  • Standalone project bootstrap (Next.js + Supabase)
  • GSM + SMS-OTP auth (provider-agnostische stub)
  • Sessies + role-based access
  • Box aanmaken · box-membership
  • Uitnodigingen: eenmalig, tijdgebonden, intrekbaar
  • Accept-flow → deelnemer gekoppeld aan box
  • RLS op elke tabel · audit-log + events-skelet
Non-goals (later)

Bewust uitgesteld

  • Content-upload & processing → Fase 2
  • Wallet, tokens, rentals, payouts → Fase 3
  • Moderation console, AI-screening → Fase 4
  • Echte SMS-provider & PSP → compliance-spoor
  • Native mobiele app (Fase 1 = web, mobile-first)
  • SX-koppeling
Waarom hier beginnen

Zonder geverifieerde accounts, boxen en veilige uitnodigingen kan niets anders bestaan. Dit is ook de laag met de meeste beveiligings- en privacy-consequenties — die willen we goed hebben vóórdat er content of geld doorheen stroomt.

03

Databaseschema

Zeven tabellen. Publieke identifiers zijn codes; het GSM-nummer staat versleuteld en is nooit een sleutel. Rollen zijn aparte, scoped rijen — één persoon kan verschillende rollen in verschillende boxen hebben.

create table account (
  id            uuid primary key default gen_random_uuid(),
  public_id     text unique not null,          -- USR-/CRT-…
  phone_enc     bytea not null,                -- versleuteld, nooit plaintext
  phone_hash    text unique not null,          -- HMAC, voor lookup zonder ontsleutelen
  status        text not null default 'active',  -- active/suspended/restricted
  phone_verified_at timestamptz,
  created_at    timestamptz not null default now()
);

create table account_role (
  id         uuid primary key default gen_random_uuid(),
  account_id uuid not null references account(id) on delete cascade,
  role       text not null,                    -- platform_operator/moderator/box_admin/creator/user
  box_id     uuid references box(id) on delete cascade,  -- null = platform-breed
  unique (account_id, role, box_id)
);

create table box (
  id          uuid primary key default gen_random_uuid(),
  public_id   text unique not null,            -- BOX-…
  name        text not null,
  description text,
  created_by  uuid not null references account(id),
  status      text not null default 'active',
  created_at  timestamptz not null default now()
);

create table box_membership (
  id         uuid primary key default gen_random_uuid(),
  box_id     uuid not null references box(id) on delete cascade,
  account_id uuid not null references account(id) on delete cascade,
  role       text not null,                    -- box_admin/creator/user
  status     text not null default 'active',
  invited_by uuid references account(id),
  joined_at  timestamptz not null default now(),
  unique (box_id, account_id)
);

create table invitation (
  id            uuid primary key default gen_random_uuid(),
  public_id     text unique not null,          -- INV-…
  box_id        uuid not null references box(id) on delete cascade,
  target_role   text not null,                 -- creator/user
  target_phone_enc bytea not null,
  target_phone_hash text not null,
  token_hash    text unique not null,          -- alleen de HASH; token zit in de link
  invited_by    uuid not null references account(id),
  expires_at    timestamptz not null,
  used_at       timestamptz,
  revoked_at    timestamptz,
  created_at    timestamptz not null default now()
);

create table audit_log (            -- append-only
  id         bigserial primary key,
  actor_id   uuid,
  action     text not null,
  target_type text, target_id text,
  metadata   jsonb, reason text,
  created_at timestamptz not null default now()
);

create table events (               -- event-backbone (staat in voor Kafka)
  id         bigserial primary key,
  type       text not null,                    -- INVITATION_SENT, MEMBERSHIP_CREATED…
  payload    jsonb not null,
  created_at timestamptz not null default now(),
  processed_at timestamptz
);

create table app_config (           -- configureerbare defaults
  key text primary key, value jsonb not null
);
-- seed (Fase 3 gebruikt deze; nu alvast vastgelegd):
--  tokens_per_euro=100 · creator_split=0.80 · payout_threshold_eur=50 · rental_hours=24
Waarom phone_hash naast phone_enc

Je moet een nummer kunnen opzoeken (bestaat dit account al? matcht de uitnodiging?) zónder het te ontsleutelen. Een HMAC-hash maakt gelijkheids-lookups mogelijk terwijl het echte nummer versleuteld blijft.

04

Row-Level Security

Elke tabel krijgt RLS aan. De browserclient kan bijna niets direct; gevoelige schrijfacties lopen via server-routes met de service-role. Twee voorbeelden van het patroon:

-- box_membership: je ziet alleen boxen waar je zelf lid van bent
alter table box_membership enable row level security;

create policy "leden zien hun eigen memberships"
  on box_membership for select to authenticated
  using (account_id = auth_account_id());

-- invitations: NIEMAND leest ze via de client; alleen server (service-role).
alter table invitation enable row level security;
-- (geen select/insert policy voor 'authenticated' → default deny)

-- box: alleen platform-operator of box-admin kan een box updaten
create policy "box-admin beheert eigen box"
  on box for update to authenticated
  using (exists (
    select 1 from account_role r
    where r.account_id = auth_account_id()
      and (r.role = 'platform_operator'
        or (r.role = 'box_admin' and r.box_id = box.id))));
Twee sloten. De server-route controleert de rol (applicatielaag) én de RLS-policy controleert de rij (databaselaag). Eén bug in de app lekt dan nog geen data, want de database weigert de rij alsnog. Uitnodigingen hebben bewust géén client-leespolicy — ze zijn alleen server-side benaderbaar.
05

OTP-adapter (provider-agnostisch)

De hele auth-flow praat met één interface. In Fase 1 draait de stub die de code naar de serverconsole logt; de echte provider implementeert later dezelfde interface — zonder dat de app-code verandert.

// lib/auth/otp-adapter.ts
export interface OtpSender {
  send(phoneE164: string, code: string): Promise<void>;
}

// lib/auth/otp-stub.ts  — Fase 1
export const stubSender: OtpSender = {
  async send(phone, code) { console.log(`[OTP] ${phone} → ${code}`); }
};

// later: twilioSender / messageBirdSender implement OtpSender — één regel omzetten.

OTP-flow

  1. POST /auth/otp/start → normaliseer naar E.164, rate-limit per nummer + per IP, genereer 6-cijferige code, sla hash + expiry op (5 min), roep OtpSender.send aan.
  2. POST /auth/otp/verify → vergelijk hash, check niet-verlopen & pogingslimiet, maak/vind account, zet phone_verified_at, open sessie.

Regel voor elk endpoint

Autorisatie is server-side en wordt per verzoek herbepaald — nooit een clientclaim over rol of eigenaarschap vertrouwen. Elke schrijfactie die een mens of rol raakt, schrijft een audit-regel.

07

Uitnodiging-token · veiligheid

Opslag

Alleen de hash

De rauwe token zit alleen in de SMS-link. In de database staat token_hash — zoals een wachtwoord. Lekt de DB, dan zijn de links onbruikbaar.

Eenmalig

Used & revoked

used_at maakt hem na één keer ongeldig; revoked_at laat het platform of de box-admin hem intrekken vóór gebruik.

Tijdgebonden

Expiry

expires_at (bv. 72 uur). Verlopen tokens worden geweigerd, ook al zijn ze nooit gebruikt.

Gebonden

Aan het doelnummer

Accepteren kan alleen als het OTP-geverifieerde nummer gelijk is aan target_phone_hash. Een doorgestuurde link werkt niet voor iemand anders.

Accept-flow in het kort: open link → OTP op jouw nummer → server checkt: token bestaat, niet verlopen, niet gebruikt, niet ingetrokken, én jouw geverifieerde nummer matcht het doel → membership aangemaakt met de bedoelde rol → token op used_at → audit + event.

08

Audit & events

Twee lichte helpers die vanaf Fase 1 overal meelopen, zodat latere fasen er alleen op hoeven aan te haken.

audit.ts

Onveranderlijke trail

writeAudit(actor, action, target, meta) — schrijft naar audit_log bij elke gevoelige actie (account aangemaakt, box aangemaakt, invite verstuurd, membership gemaakt). Nooit ge-update of verwijderd.

events.ts

Backbone-skelet

emit(type, payload) — append naar events. In Fase 1 nog zonder consumers; het legt de rails zodat Fase 2–4 (notificaties, moderatie) er reactief op inhaken.

Security-checklist Fase 1

  • ✓ GSM versleuteld at-rest (phone_enc), HMAC voor lookup — geen plaintext-nummers.
  • ✓ OTP: 6 cijfers, 5 min geldig, pogingslimiet, rate-limit per nummer én per IP.
  • ✓ Uitnodiging-tokens gehasht opgeslagen, eenmalig, tijdgebonden, intrekbaar, aan doelnummer gebonden.
  • ✓ RLS aan op elke tabel; service-role alleen server-side (persistSession:false).
  • ✓ Autorisatie per verzoek server-side herbepaald; geen clientclaims vertrouwd.
  • ✓ Audit-regel bij account-creatie, box-creatie, invite, accept.
  • ✓ TLS in transit; secrets alleen server-side; geen PII in logs.
11

Klaar wanneer…

Fase 1 is af — en klaar voor Fase 2 — wanneer dit end-to-end werkt en getest is:

  1. Een platform-operator kan inloggen via OTP en een box aanmaken.
  2. De operator/box-admin kan een creator uitnodigen op een GSM-nummer; die ontvangt een link (stub → console), verifieert via OTP, en wordt lid van de box als creator.
  3. Dezelfde flow werkt voor een user-uitnodiging.
  4. Verlopen / gebruikte / ingetrokken / verkeerd-nummer-tokens worden correct geweigerd.
  5. Elke stap staat in de audit-log; events bevat de bijbehorende event-regels.
  6. De testsuite (unit + integration + security) draait groen; RLS-grenzen zijn bewezen.
Geen content · geen geld · geen moderatie — dat is Fase 2–4
